# GPU release validation campaign (2026-08-18)

## Purpose

This campaign tests the current Mosaic source snapshot, not historical output
directories. One job supplies one distinct capability claim. Accelerator
partitions are alternatives selected by Slurm; the same trajectory is not
duplicated on every GPU model unless a hardware-reproducibility experiment is
explicitly requested.

The campaign is generated by:

```bash
python scripts/rfd3_mosaic/submit_gpu_release_gates.py --list
python scripts/rfd3_mosaic/submit_gpu_release_gates.py --tier core
python scripts/rfd3_mosaic/submit_gpu_release_gates.py --tier core --submit
python scripts/rfd3_mosaic/submit_gpu_release_gates.py --tier extended --submit
```

Every submitted YAML is frozen under one timestamped campaign directory. The
manifest records the Git revision, scientific claim, requested design count,
profile, validation result and submission output.

## Core gates

| Gate | Evidence required |
| --- | --- |
| `fixed-components` | Exact fixed components, complete symmetry orbit, continuous clash-free output |
| `locked-packing` | Two outputs from one task; fixed arrangement unchanged; generated-only interface guidance and final interface audit |
| `guided-packing` | Two outputs from one task; internally rigid motif; joint generated-patch plus radial/axial/rotation transaction; final packing audit |
| `d3-dynamic` | Six D3 actions, two independently mobile motif orbits, exact internal geometry and atomic rollback/acceptance evidence |
| `c4-c2-quotient` | Two physical C4/C2 quotient copies rather than a fake four-copy full orbit |
| `t-static` | Complete 12-action tetrahedral execution and exact fixed-orbit audit |
| `t-packing` | Tetrahedral graph guidance reaches final written-structure interface and scaffold audits |

The locked and guided jobs deliberately request `sampling.designs: 2`. This is
the first GPU gate for multi-design fan-out, per-design audit isolation and
aggregate accepted/rejected yield.

## Extended finite-group gates

`o-static` and `i-static` are short 10-step software execution canaries for 24
and 60 proper rotations. They use the A100/H100 partition pool because the
explicit-all-copy reference backend is intentionally memory intensive. Passing
these jobs proves transform transport, fixed-orbit preservation and output
closure; it does not establish biological suitability or generated-interface
quality for O/I cages.

Dynamic T/O/I mobility remains outside this campaign because the public
compiler currently fails closed for polyhedral component optimization. It must
not be represented as validated by a static canary.

### Historical O/I result and required rerun

The first extended jobs (`5752498` for O and `5752499` for I) are not valid
negative scientific results.  Their public designs passed complete CPU
geometry and RFD3-input prevalidation, but the frozen runtime failed before
diffusion in AtomWorks `UnindexFlaggedTokens` with duplicate token indices.
Consequently they produced no structures and say nothing about O/I backbone
quality. Job `5753687` was a later I resubmission, but no completed audited
result was recorded in the evidence collected for this document. As of
2026-08-20 it remains pending with no run directory. The old T/O/I jobs
`5752497--5752499` remain failed process executions with zero output
structures; all three passed RFD3 input prevalidation first. Their worker
stderr confirms one shared pre-diffusion failure in
`UnindexFlaggedTokens`: a token-level AtomArray was sliced a second time and
Biotite rejected duplicate symmetry-expanded bond indices. Commit `dab8103`
constructs those masks directly from annotation arrays, without slicing the
bond graph; its focused regression tests pass `2/2`. Fresh T/O/I canaries are
still required to validate the repair in the complete GPU pipeline.

Current source revision `6b67605` again passes CPU construction for the full
24-chain O input (4,560 atoms/696 residues) and 60-chain I input (11,400
atoms/1,740 residues).  This is necessary but not sufficient: both still need
one fresh 10-step A100/H100 execution gate from the current frozen source.
These jobs are software transport/closure tests, not claims of biologically
useful O/I cages.

The O/I YAMLs are explicitly documented as transport canaries, with fixed
initial radii of 110 A (O) and 180 A (I), only ten generated residues at each

scaffold question.  An I fixed-orbit failure after the 50-step rerun must be
treated as a hard-projector/runtime defect rather than excused as insufficient

## Supplied multi-interface gates

Ordinary multi-seed intent files are not submitted directly. Each must first
run `resolve`, produce a ranked `selected/rank_0001_*.yaml`, and pass strict
`validate` replay. Only that frozen selected YAML may be submitted. Required
follow-up cases are:

1. pre-positioned two-seed C3 supplied geometry;
2. user-connected two-seed C3 with unknown relative input pose;
3. three-participant C3 quotient seed;
4. three-seed T with user-declared polymer connections.

If a resolver produces `selected=0`, that is a CPU/software blocker. It is not
a GPU experiment and must not be forced into the queue.

## Ho-Yeung RFdiffusion Interface-Seed baseline

The authoritative baseline source is the separate repository
`RFdiffusion_interfaceseed`, commit `a81ed19`, branch `interface_seed`. Its
published example uses the following protocol (the example count of 10 is
increased to the requested formal dataset of 1000):

```text
symmetry=C3
T=50
num_designs=1000
input=examples/input_pdbs/7mwr_interface.pdb
contig=Y211-241/70-100/X165-194
motif_drag=True
asy_motif_weight=1
asy_motif_rot_range=[180,180,180]
asy_motif_dist=25
asy_motif_dist_range=5
olig_contacts=(weight_intra=1, weight_inter=0.1)
guide_scale=2.0
guide_decay=quadratic
```

Its timestep update translates the two-chain interface motif toward the
midpoint of adjacent generated-subunit COMs before the next `sample_step`. It
does not perform a rigid rotational packing proposal. Mosaic's legacy C5
`scaffold_boundary` mobility pilot is therefore not the exact baseline and
must not be labelled as such.

The fair comparison keeps input, symmetry, contig length range, timesteps and
design count fixed. It reports generated count, accepted yield, motif/interface
RMSD, symmetry error, chain breaks, clashes, interface residue coverage,
continuity, orientation/shape proxies, minimum edge distance, morphology and
runtime. Mosaic superiority is a result to measure, not an assumption.

Use `submit_hoyeung_lhd101_1000.sh pilot` first to verify the original RFdiffusion
environment/checkpoint and measure time/storage, then use `full`. The full run
uses 100 disjoint Slurm array chunks of 10 designs (maximum 16 concurrent GPUs)
covering output indices 0--999. All scientific overrides remain identical to
the published command. Because its published default is
`inference.deterministic=False`, scheduler chunks sample the same protocol but
do not reproduce the single-process RNG stream byte for byte.

## Multi-design random stream

RFD3 seeds the inference engine once with `sampling.seed` and evaluates
`n_batches` sequentially. Output IDs contain the batch index, while current
metadata records the common base seed. Therefore a result is identified by
`(source snapshot, frozen input hash, base seed, batch index)`. Replaying one
late batch currently requires replaying the preceding RNG stream; a future
per-design derived-seed mode may improve random access but is not required for
the present throughput gate.
